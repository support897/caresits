One Firebase project (caresits-812a0). Live rules baseline: /home/user/cs/accounts/firestore.rules.live-2026-11-03.txt. New rules are written by the rules owner into packages/rules/firestore.rules and proven by emulator tests; they stay backward compatible with existing data.

## Existing (live) - keep working
- profiles/{uid}: side("family"|"carer"), displayName, postcode, photoUrl, about(<=300), card{...allowed keys only}, looking{musts,prefs}, updatedAt. Read by any signed-in non-anonymous user. Owner writes only.
- relationships/{pairId} (pairId = sorted uids joined; see pairIdFor): members[2], familyUid, carerUid, state pending|contact|hired|blocked, createdBy. messages subcollection (append-only): {from, kind text|photo|photoAsk, text<=1000, img?, at==request.time}.
- users/{uid}/... owner-private: children, dayStory, documents (qualification docs), recentlyDeleted, messages (old).
- verified/{uid} + verifyRequests/{uid}: SERVER/ADMIN-written verification records. Client may only create a verify REQUEST. A carer shows "Verified" ONLY if verified/{uid} (or a document with checkedOn/verifiedBy written by server) says so.
- careSpaces/{spaceId} (+members/{uid}{role admin|regular|limited|viewer,status active|removed,perms}, children, dayStory, calendar, shopping, messages). Membership-based access (csMember/csRole).
- _entitlements/{uid}: server-written only (RevenueCat webhook). Clients never write.

## Backend safety details (additive; no existing path is renamed)
- `profiles/{uid}.card` accepts the v2 marketplace fields listed above. It never stores a qualification summary or any client-written `verified`, `checkedOn`, or `verifiedBy` value. `lastActive` is a display hint only, not a trust signal.
- `users/{uid}/documents/{docId}` is owner-uploaded qualification evidence. A client may create it only with `status: "submitted"`; clients cannot update its status or set `checkedOn` / `verifiedBy`. Only the trusted verification function changes a record to verified. The old relationship read grant for qualification evidence remains in the live rules baseline.
- `careSpaces/{spaceId}/medical/{childId}` is a non-sensitive index/metadata document. To honor independent permissions, data lives in `careSpaces/{spaceId}/medical/{childId}/allergies/{recordId}`, `.../medication/{recordId}`, and `.../emergency/{recordId}`. Allergy reads need `members/{uid}.perms.allergies`; medication reads need `perms.medication`; emergency details are admin-only. Client writes are admin-only and must atomically create a matching `careSpaces/{spaceId}/alerts/{alertId}` with `kind: "medical-change"`, `by`, `at`, `childId`, `section`, and `recordId`. Medical deletes are server-only.
- `careSpaces/{spaceId}/alerts/{alertId}` is append-only. Medical-change alert writes must match the medical document changed in the same batch. Safety/allergy push delivery ignores notification opt-outs.
- `careSpaceInvites/{inviteId}` stores `{spaceId, role, createdBy, createdAt, expiresAt, usedBy}` and may include `perms`. Invite roles are only `regular`, `limited`, or `viewer`; `usedBy` and the new active member are written together. A join cannot choose a different role, grant permissions, or use an expired token. A targeted handoff invite includes both `targetUid` and `bookingId`; rules check that the named carer has an accepted booking with the CareSpace owner, and only that UID may accept it. The Handoff screen still does not surface the generated code (out-of-scope UI blocker).
- `careSpaces/{spaceId}/members/{uid}.perms` contains optional booleans `allergies`, `medication`, `photos`, `calendar`, and `privateMessages`. A missing permission means false. The member's `status` must be `active` for access; setting it to `removed` revokes access at once.
- `relationships/{pairId}/bookings/{bookingId}` starts as `requested` from the family. Only the carer may decide `accepted` or `declined`; either relationship member may cancel a requested or accepted booking. `relationships/{pairId}/checkins/{id}` is an append-only in-booking safety check-in and requires an accepted booking. `careSpaces/{spaceId}/checkins/{id}` also requires an accepted booking bound to the space owner and carer; the current family safety-screen write lacks those relationship IDs and remains blocked until its out-of-scope payload is fixed.
- `careSpaces/{spaceId}/calendar/{eventId}` time-off requests start as `requested`. Only admins approve, decline, or propose a swap. Client-created calendar events cannot pretend to be bookings; booking calendar entries come from the trusted booking flow. Calendar records are not client-deleted.
- `users/{uid}/blocks/{otherUid}`, `users/{uid}/saved/{personUid}`, `users/{uid}/emergencyContacts/main` (up to three contacts in its `contacts` list), and `users/{uid}/prefs/main` are owner-only. `users/{uid}/prefs/main` has choices for messages, bookings, care updates, requests, calendar, shopping, allergy changes, a daily recap, and work-time muting. Safety and allergy pushes cannot be disabled.
- Known out-of-scope mismatch: `apps/carespace/src/data/medical.ts` still writes allergies, medication, and emergency details to one combined `careSpaces/{spaceId}/medical/{childId}` document, and its alerts omit required child/section/record IDs. Rules require separate section records plus matching alerts; do not loosen them to accept the combined app write.
- `_rateLimits/{uid_action}` stores server-only short-window counters for callable and push limits. `_dailyRecapRuns/{uid_date}` prevents duplicate daily recap pushes. `_entitlements/{uid}`, `verified/{uid}`, `_rateLimits/{uid_action}`, and `_dailyRecapRuns/{uid_date}` are never client-writable.
